# D2／G-08 の脅威モデル（2026-11-02、Claude）

**設計案であり、未実装・未承認。** 鍵は生成も配布もしていない。ユーザーが管理者と信頼境界を決めるまで、署名機構は実装しない。M1 は 2/8、NOT ACCEPTED のまま。
目的：「承認」「署名」「DB の整合性」「本人認証」を混同しないために、**誰が何をでき、いまの仕組みが何を防ぎ・何を検出し・何を証明しないか**を一箇所に固定する。

## 1. 守りたいもの（資産）と、DB が主張してよいこと
| 資産 | 主張してよいこと | 主張してはいけないこと |
|---|---|---|
| `evidence_heads`／`article_heads`（現行版） | 承認された batch の `after` を指している（DB-18 が再生で照合） | その承認を誰が行ったか |
| `update_batches`（`approved`）・`update_events` | 記録された順序で矛盾がない | 承認が**独立 QA の結果**に基づくこと、ユーザーが公開を承認したこと |
| `qa_json`（QA 結果） | `batch_input_sha`・`articles_sha256` が**この更新に結びついている** | 結果を**誰が作った**か（偽造できる） |
| `revision_reasons` | 呼び出し側が渡した理由をそのまま保存 | 理由が正しいこと、`actor` が本人であること |
| 原典の登録・検証イベント | SHA・保存ファイルの照合 | 公式サイトの真正性（収集記録から取った観察でない限り） |

**DB の `approved` は「データの有効化」であり、公開の承認ではない**（`docs/architecture/M1_FINAL_APPROVAL_ITEMS.md` の項目 7 と同じ）。

## 3. いまの仕組みが「何であって何でないか」
- `sogh_write_ok`＝**能力**。誤設定の接続を止める。**認証でも署名でもない。**
- DB-17＝既知の SQL オブジェクトの一致の**検出**。データ全体の外部署名ではない。DB-18＝承認・rollback の記録と head の整合の**検出**。作成者本人性・QA の真正性・公開の承認は**証明しない**。
- チェックサム（移行・再生）＝自己申告と同じ場所にある限り、敵対的な改ざんの防止にならない。
- QA の `batch_input_sha`／`articles_sha256`＝**この更新への結びつき**。結果の作成者の証明ではない。
- 承認台帳の HMAC＝対称鍵。鍵を持つ検証側＝偽造できる側。AI と同じ実行アカウントに鍵を置けば、分離にならない。

## 4. 独立に再現した事実（`SYNTHETIC_ONLY`）

- 能力の無い接続は、head・batch・event・reason のどれも書けない（6 種の文で確認）。

## 5. 署名を入れる場合に証明させるべきこと（案）
承認する「文」を正規化して署名する。最低限、次を含める：記事／root／version、原典スナップショットの hash 群、本文の content hash、操作（finalize／rollback／publish）、対象環境、**直前の head の hash**、registry の版、nonce、有効期限、鍵 ID。
- 検証側は**公開鍵だけ**を持つ（非対称）。署名は「QA 実行者の結果」と「ユーザーの公開承認」で**別の文・別の鍵**（混同しない）。
- nonce は追記専用の表で再利用を拒否（再送攻撃）。鍵の失効・ローテーション・紛失時の復旧手順を先に決める。
- 署名の検証は `finalize` の同一トランザクションの中、失敗は全体を巻き戻す（現在の異常系と同じ）。
- **DB 全体を古い整合した版へ戻す攻撃**は、DB の中の署名では防げない。必要なら外部の固定点（追記専用の記録の hash を別の場所へ定期的に控える）を別途設計する。

## 6. ユーザーが選ぶ構成の候補（採用していない。利点・リスク）
| 案 | 概要 | 利点 | リスク・残る点 |
|---|---|---|---|
| A 別 OS アカウントの承認 broker | 承認専用アカウントが署名し、AI の実行アカウントは公開鍵と broker の呼び出しだけ。最小 ACL | 追加費用が小さい | 同じ管理者・同じ端末は残る。broker 自体が攻撃面 |
| B 別端末／別サービスの承認器 | 署名を別の機器・サービスで行い、実行側は検証だけ | 実行端末が侵害されても署名を作れない | 費用・可用性・運用（誰が起動するか） |
| C ハードウェア鍵（利用者の操作で署名） | ユーザーが物理的に操作したときだけ署名。公開鍵を DB／リポジトリに固定 | 「本人の操作」に最も近い。AI は署名できない | 画面・復旧（紛失）・複数端末の設計が要る |
| D 組み合わせ | QA 実行者の署名（別の鍵）＋ユーザーの公開承認（C など） | 「QA がしたこと」と「承認」を分離 | 部品が増える |
いずれも**ユーザーが管理者と信頼境界を先に決める**。鍵を repo・プロンプト・AI と同じ実行アカウントのファイルに置くだけでは分離にならない。対称 HMAC を使うなら、検証用 secret を AI 側に渡せば偽造権限にもなる。

## 7. ユーザーの決定が要ること
鍵の管理者と保管場所／紛失時の復旧／QA 実行者を別の主体として扱うか／署名の対象（有効化のみか、公開承認まで）／公開の承認を DB の `approved` とは別に扱う運用／外部の固定点を取るか。
これらが決まるまで、Claude は契約（署名する文の形、拒否する負例）の案までを作り、**実装・鍵の生成はしない**。Work は隔離したモックの検証器を実装できる（実鍵なし）。

## 8. 採用した場合の負例（案）
署名なし／別 nonce の再送／有効期限切れ／別の記事・別の head の署名／QA 実行者の署名を公開承認として提示／失効した鍵／署名の文の一部（環境・操作）の改変／署名は有効だが `batch_input_sha` が違う／鍵 ID の不明、がすべて `finalize` で全体拒否され、DB が前後で同一であること。
