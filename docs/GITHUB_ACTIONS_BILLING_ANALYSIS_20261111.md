## 2. 原因の判定
**あなたの見立て（無料枠の上限超過）と整合する。最も可能性が高い。** ただし請求画面を見ていないので「確定」ではなく**最有力**。

- 個人（Free プラン）の private リポジトリの Actions は**月あたりの含まれる分数に上限**がある（公式の目安：Free は 2,000 分／月、Pro は 3,000 分／月。**数値は GitHub の請求画面で要確認**）。上限を使い切り、かつ**支出上限（Budget）が $0** だと、追加の分は課金できず、新しいジョブは**開始されない**。このときの標準のメッセージが上記の文言（「支払いが失敗した」**または**「支出上限を上げる必要がある」の二択の文言なので、支払い履歴が無くても出る）。
- 計算：成功した 147 run × 約 28 分 ≒ **約 4,100 分**（失敗・キャンセルした run を含めるとさらに多い）。Free の 2,000 分は 11/1 の途中で尽き得る。**数字が上限（Pro でも 3,000）を超えて見える点は、分の数え方（切り上げ・キャンセル・課金サイクルの開始日）の誤差か、上限の数値が上記と違う可能性があり、請求画面で確認が必要。**
- もう一つの可能性（低い）：支払い方法の登録があり、**実際に請求が失敗している**。この場合も同じ文言になる。請求画面の「支払い情報」「ロック」の表示で判別できる。
- 設定の問題・ワークフローの文法・テストの失敗ではない（ステップが 0 個で、すべて同一の注釈）。

## 3. 確認方法（本人がブラウザで。5 分）
1. GitHub → **Settings → Billing and plans**（個人アカウントの設定）。
2. **Usage this month（または Usage）**で「Actions minutes」の使用量と上限、**リセット日**（課金サイクルの次回日）を確認。
3. **Budgets and alerts**で Actions の予算（既定は $0）と「Stop usage when limit reached」を確認。
4. **Payment information**で支払い方法の有無・失敗の有無を確認。
→ 結果（上限・使用量・リセット日）を教えてもらえれば、私が表に反映します。（私が API で読むには `gh auth refresh -s user` が必要。認証スコープの変更なので、ご承認があれば実施します。）

## 4. 解決策（効果が大きい順）
**重要：上限が復活（リセット）しても、今のワークフローと PR の数のままだと、1〜2 日で再び尽きる。** 使用量そのものを減らす必要がある。

| 案 | 内容 | 効果・費用 | 備考 |
|---|---|---|---|
| **S1（推奨）：ワークフローの節約** | ①`paths-ignore`：`docs/**`、`strategy/**`、`*.md` のみの変更では実行しない（Draft PR の大半は文書）②`pytest-windows` と `pytest-py311` を PR では実行せず、**master への push と週次のみ**にする（Windows は 2 倍課金）③Draft PR では実行せず、`ready_for_review` または手動（`workflow_dispatch`／ラベル）で実行する | 1 run が **28 分 → 約 7 分**（ubuntu 1 本）、run 数も大幅減。**合計で 1/10 以下**の見込み。**費用 0** | `.github/workflows/tests.yml` の変更＝技術変更なので**本人の承認と、別 PR・独立 QA** が要る。必須チェック名 `pytest` は維持 |
