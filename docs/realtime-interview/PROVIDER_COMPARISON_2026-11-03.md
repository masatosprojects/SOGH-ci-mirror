## 5. 方式A と方式B を分けた分析
| 観点 | 方式A：STT → LLM → 検証 → TTS → アバター | 方式B：リアルタイム音声モデル → アバター |
|---|---|---|
| **安全性（発話前の検証）** | **発話前に全文を検証できる**（文字の段階で `guards`・根拠・数字・範囲を検査）。違反は発話されない | **音声が生成・再生された後でしか検証できない**可能性が高い（ネイティブ音声は音声のみを出力し、テキストは文字起こしから）。違反の**防止ではなく検出と遮断** |
| 公式情報の扱い | 公式事実に触れる質問は、検証済みの文を読み上げるだけ | モデルが公式情報を**言い換え・補完**するリスク。逐語の読み上げが保証されるかは【未検証】 |
| 遅延 | 段階の合計（認識の確定＋LLM＋検証＋合成＋映像）。**目標 2 秒（p95）は、実測するまで達成可能かわからない** | 低遅延の可能性。実測が要る |
| 自然さ | 割り込み・間・相づちは自前で実装。合成の抑揚は部品次第 | 自然さが期待できる（全二重を含む）。**人の評価が要る** |
| 実装 | 部品は交換可能。ターン制御・割り込み・世代管理を自前で作る | 提供者に依存。制御（質問の固定、時間）が弱くなる |
| 費用 | モデル部分は低め（上の【算】）。段階ごとの再試行 | モデル部分は低〜中。アバターが主要 |
| データの流れ | 段階ごとに送信先が増える（同意の記述が増える） | 送信先は少ない。音声全体が 1 事業者へ |
| 障害時の縮退 | 段階ごとに文字へ縮退できる | 提供者の障害で全体が止まる。方式A へ切替できる設計が要る |
### 方式B を使う場合の提案（発話の種類による許可）
| 種類 | 許可 | 制御 |
|---|---|---|
| 相づち・短い応答（「はい」「なるほど」） | 方式B 可 | 許可リストの語。出力の文字起こしを**事後に照合**し、リスト外・長さ超過なら即取消 |
| つなぎ・案内（「続けてください」「少し間を置きます」） | 方式B 可（固定文を指示） | 同上＋逐語の一致を監査 |
| 時間の案内（残り時間） | **コントローラが数字を渡した固定文**のみ | 数字を勝手に生成させない |
| **質問の本文・追質問** | **方式A（検証済みの文の読み上げ）に限る** | 発話前に全文を検証 |
| **公式情報に関する発話**（時間・形式・評価観点・日程） | **方式A に限る**。根拠の版を併記 | 未確認は「公式には確認できていません」の固定文 |
| 受験生への評価・励まし | 面接中は出さない（振り返りで） | — |
**監査と遮断**：出力の文字起こしを `guards` と許可リストで即時に照合 → 違反なら応答を**取消**（バッファと映像の旧世代も取消）→ 固定の言い直しの文 → 以後その面接は方式A へ切替、記録に残す。全文の事前検証ができない以上、**方式B の全面採用は、実測（違反の発生率・逐語一致の率）が示されるまで承認しない**。
