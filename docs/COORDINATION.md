## 最優先：自律計画・依存隔離の3AI運用（2026-11-07、ユーザー明示方針）

**適用順位と目的**：本節はユーザーが明示した**「指令塔から個別AIへ新作業プロンプト・CMD Issueを発行する方式の停止」**と**「各AIが他AIを待って全面停止せず、SOGH完成に向け独立した前進作業を自ら探す」**という運用変更を定める。**本節が下の旧「1指令/指令塔による後継Issue発行」や「タスク着手前の指示Issue必須」と矛盾する場合、本節を優先**する。STR-067の事業判断ではなく、3AIの作業プロセスのルール。既存のユーザー明示の最終決裁・安全条件、AGENTS.mdの担当/独立QAの分離は変更しない。

### 指令塔と3AIの役割
- **各AIが自律的に計画する**：Work＝自分の製品/Windows/M1領域、Claude＝独立QA/自分の契約領域、Antigravity＝隔離されたローカルLLM研究領域。各AIが自分で`next_action`を考え、**既に許可済みで、他者の新しい成果や本人承認を必要としない小さな仕事**なら自身の実行可能なセッション内で続ける。ユーザーが本人チャットで直接指示することもあるため、重複/競合の整合は当該AI自身が扱う。新しい`CMD-*`の指示票を指令塔が量産しない。
- **指令塔は監査・整流役**：GitHub #199の本人RESULT/最新head・#214の状態・承認済みSTR/製品M1ゴールを読み、**目的ずれ・同一仕事の重複・長期足踏み・独立QAの不足・担当/権限の越境・費用/安全上の懸念**を検出してユーザーに簡潔に報告する。原則として個別次作業プロンプト/差分指令をGitHubに出さず、必要時に**事業方針や担当衝突の判断をユーザーへ提案**する。技術変更の指示や実行を代行しない。
- **ユーザーが最終決裁する**：新しい事業判断、担当境界の変更、製品M1正式受容・技術PRの統合、実受験生データ/本番DB、常時監視・実通知、モデル実推論/高負荷、追加課金、署名/本人承認の代理などは、これまでどおり該当操作に対する具体的な本人許可が必要。自律計画は**承認拡大ではない**。

### 他AI依存は「作業単位」で隔離し、セッション全体を止めない
1. 次に行う仕事を、`READY_INDEPENDENT`（自分の担当・許可内で他AIの新成果を待たず実行可能）、`WAITING_DEPENDENCY`（特定の他AI成果/確認が必要）、`REQUIRES_USER_APPROVAL`（必要な本人承認なし）、`DONE_WITH_EVIDENCE`のように**小タスク単位**で分ける。待機先`dependency_owner`・固定PR SHA/証拠・`unblock_signal`を明記。古いheadのQAや他AIの仕事を自分の成果として代行しない。
2. `WAITING_DEPENDENCY`があれば**その小タスクだけ待機**し、独立して実施可能な候補を少なくとも1件探索する。候補は**元のSOGH事業目標、最初のMVPと未受容M1ゲート、安全/費用制限**に直結するものを優先する。例：Workはg2原典版/scopeの保存資料read-only照合や合成テストの不足を発見、Claudeは他headの独立QA条件/自分の契約の未決を読み取り整理（**同じ変更の独立QAを先回りでPASSしてはいけない**）、Antigravityはモデル未使用のセンサー不在/メモリ拒否の合成安全回帰や再現ドキュメントを整理。**例示は指令ではない**。その作業が他者作業と重複しないことをGitHubの最新本人REPORT/PR headで照合。
3. 進められる独立小タスクがあれば、**1件ずつ成果・固定head・PASS/FAIL/NOT_RUNを確認してから次に進む**。見かけの進捗を作るための同一テスト反復/報告書増殖、過去に却下された依存先の無断変更、権限のない自動情報取得は禁止。独立で安全なタスクが本当に存在しなければ、`NO_SAFE_READY_TASK`と理由/人間に必要な決裁事項を報告して止まる。**何かをし続けるために許可や安全条件を破らない**。
4. 実装→独立QAなどの**本質的な依存関係は残す**。ClaudeがWork/Antigravityの新headを独立QAするにはそのheadが必要。待ち時間中は他の独立タスクを行ってよいが、変更後の独立QAを旧headのPASSで代替してはいけない。監査者は、複数AIが同じ依存先を待っている場合に優先的に依存グラフ・主体/解除証拠・代替作業を点検する。

### 各AIの本人RESULTに入れる「次の2タスク」欄
各AIは**セッション開始/節目/終了時**に最新master・承認済みSTR・自担当PR headと他者の本人RESULT/QAを読む。結果は担当Issue/PRまたは#199へ本人として残す。既存のRESULTのPASS・NOT_RUN/受容区別を保ち、以下を追加する：
`roadmap_goal/M1_gate`、`achieved/fixed_SHA/self_test/independent_QA/NOT_RUN/formal_acceptance`、`blocked_items(owner,dependency,unblock_signal)`、`READY_INDEPENDENT_next_1(max_2)(objective,why_now,expected_evidence,cost_and_safety,stop_condition)`、`user_direct_status`、`user_approval_needed`、`next_review_condition`。後継タスクは**各AIが自分で選定・進行**し、指令塔からの次CMDを待たない。既存Issueの完了/依存状態と新しい自発タスクを履歴としてリンクし、指令塔がその場で直接指示しなくても他者/ユーザーが追跡可能にする。
- スケジュールは予測を断定しない。優先度は**M1の未達ゲート、重要な安全不具合、実用上の前進、独立性**に紐付ける。長期間の同種テスト/同じ保留で成果が伸びない場合、成果と阻害要因・代替の候補を示して方針修正をユーザーへ提案。報告だけを何周も作って進捗扱いしない。

### 継続性の正確な限界・ローカル安全
- この変更だけで各AIのチャット/IDEが自動的に再開・バックグラウンド常駐・無期限連続実行するわけではない。**動作中の各セッションにおける自己計画**と、再開時に本人RESULTから次へ進む形。別アプリ・セッションへ本規約を自動pushしたとはみなさない。
- ユーザーからのPC制約：Antigravityを同じゲーミングPCで開発中、ローカルLLMと十分な空きRAMの両立が難しい。**実モデルは未承認**。将来別途具体的な単発許可があっても開発保存→Antigravity通常終了→物理空きRAM`>=2200MB`と実HWiNFO CPUダイ温度センサーを確認し、安全ガード未達なら起動禁止。現在モデル推論・高負荷/強制終了・閾値緩和なし。

### 過去指令の扱い
既存`CMD-*` Issueは**履歴・証拠/未解決依存の参照先**として残す。今回の規約変更を理由に新しい`CMD`を発行・再配信せず、古いCMDコメントを受信していないAIの着手を断定しない。既存の本人ACK・RESULT/独立QAの証拠は維持。日々の自己計画と成果は各AI本人が既存の担当Issue/PR/個人REPORTに記録し、指令塔は#199/#214を**監査索引として更新してよいが指示は書かない**。

## 受信確認付き三者連携（運用手順・2026-11-07ユーザー承認C）

**承認の種類**：ユーザーがSOGH03で選択した「C｜受信確認付き三者連携」（自由記述なし）は**指令の運用方式**。新しい事業STR・製品実装の技術承認・自動起動権限ではない。参照は[#214運用監査](https://github.com/masatosprojects/SOGH-collab/issues/214)、[事業判断後ループ](../strategy/AI_COORDINATION_LOOP.md)と[#199指令ハブ](https://github.com/masatosprojects/SOGH-collab/issues/199)。既存AGENTS.mdの担当分離と事業責任者の明示承認を最優先とする。

### 三者と双方向の入力
- **ユーザー本人**：事業/技術の必要な最終承認を行い、Work/Claude/Antigravityの各チャットへ直接指示・判断・状態の目視報告を行うことがある。ユーザーの直接指示も**正規の指示入力**で、指令塔のGitHub票に存在しないことだけで無効と見なさない。機密/私的対話の全文転載は要求しない。
- **指令塔（通常ChatGPT）**：最新masterの採用済みSTR、事業MVPとM1受容条件、担当・依存・PR固定head・独立QA、GitHub Issue指示と#199索引を照合する。Issueを投稿するだけで他AIチャットを起動・pushできると主張しない。ユーザーに手動中継を常時要求せず、受信できないと確認した場合だけ対象AIチャットへのリンク中継を依頼する。
- **実行担当**：ChatGPT Work＝製品/Windows夜間ワーカー・M1の担当部分、Claude Code＝独立QA・契約と担当領域、Google Antigravity＝ローカルLLM実験準備/安全な合成検証。各自にユーザーから直接指示が来ているかを**自分のセッション内で**照合し、他AIの担当コードは変更しない。

### 指令配送と仕事の状態は**別軸**
- `command_delivery`：`DRAFT`（未公開）→`POSTED_GITHUB`（Issue/コメント作成済み、**他AIへの到達未証明**）→必要時のみ`USER_RELAYED`（ユーザーが対象AIチャットへリンクを伝えたという本人報告、本人ACKとは別）→`EXECUTOR_ACKED`（対象AI**本人**が最新指令ID・差分・固定head・次の具体作業を認識したとGitHubでACK）。`EXECUTOR_REJECTED`、`CONFLICT_REQUIRES_USER`は例外。更新された指令**差分**は以前の基本票ACKを自動継承せず、重要差分ごとに最新ACKの有無を表示。
- `task_status`：`READY_NOT_ACKED`／`ACKED_NOT_STARTED_PROVEN`／`IN_PROGRESS_REPORTED`／`WAITING_DEPENDENCY`／`DONE_WITH_EVIDENCE`／`BLOCKED`等の既存#214区分を継続。`RESULT`は指令の成否、`qa_status`は担当本人の自己試験/別担当独立QA/正式受容の違い、`runtime_presence`は指令塔の直接観測とユーザーの画面報告の区別で、それぞれ別欄。GitHubのACKでライブ稼働・技術受容を断定しない。
- `user_direct_status`：実行AIが**そのチャットで見える範囲**で`none_observed | same | compatible_parallel | conflicting | unknown`を報告。機密情報、実受験生の詳細、パスワード・秘密鍵を転記しない。ユーザーの直接指示を優先しつつ既承認STR/安全規約を破らず、GitHub票と衝突または技術/運用上の本人承認が必要なら`CONFLICT_REQUIRES_USER`で止める。指令塔が見えないユーザー直指示を勝手に推測・上書きしない。

### 1指令の必須情報／受信から次の作業へ
1. 指令塔は`command_id`・唯一のIssue URL、`roadmap_goal`（事業の目的/関連する承認済みSTR）・`m1_gate`（該当時）、`why_now`・実行担当/所有範囲、`fixed_master/head`・`deliverable`・`acceptance_evidence`・`qa_owner`、`dependency/blocker/unblock_signal`・`safe_independent_next_actions`（最大2件）・`stop_condition`・`out_of_scope`・費用/本人承認条件を短く示す。Issue/PR/本人結果を読む前に、新指令の重複を作らない。
2. 実行担当はセッション開始時・終了時、最新masterと自身のIssueの**本文＋新しいコメント**、#199/#214、担当PR HEAD、直近本人最終報告を再取得する。直接ユーザーチャットの指示を照合し、GitHubに`ACK: command_id / command_delta_id / master_sha / fixed_heads / user_direct_status / chosen_next_action / blockers`を残す。ACKまでは配達未証明。差分を読んだが自分のセッションで着手できなければ理由/必要なユーザー支援を明記。
3. `WAITING_DEPENDENCY`は**すべてを止める意味ではない**。依存した個別操作のみ止め、承認済みの担当範囲・低コスト・合成/読み取り専用で独立な小さな前進作業が可能なら最大2つを優先実施する。依存側の新しい固定head/独立QA/承認が到着したら、指令塔は**既存票に解除シグナル・次の具体作業を差分コメント**して最新差分ACKを確認。外部依存により他作業も不能な場合は根拠付き`WAITING_DEPENDENCY`。進展のない再試験・同一報告書の往復は行わない。
4. `RESULT`には指令ID・受信した差分・ユーザー直接指示の整合（非機密）・実headと環境・PASS/FAIL/NOT_RUN・独立QA者・M1/Phase正式受容と区別した到達範囲、次担当/次に着手可能な小さな仕事と依存を残す。#199本人FINAL REPORTと担当Issue/PRで固定証拠を更新する。`DONE_WITH_EVIDENCE`でも承認済みとは限らない。
5. 指令塔は各回答/新しい重要報告で全員の`delivery`・`task`・`runtime`・`QA`・`formal_acceptance`を更新し、固定headと次担当の認識違い、指令番号の誤参照、ユーザー直接指示との衝突を検出する。有効な後継指令が**本当に無い**証拠付き完了者にだけ新Issueを1件作り、重複や依存待ちは既存Issueに差分追記する。本人ACK/起動までは配送完了と称しない。

### 正式な禁止境界
- GitHubへの投稿はAIチャットへの通知/自動再開を実現しない。配信機構/有料外部サービス/自動タスクの新規開始やWeb監視は**別の明示承認**が必要。
- 本番DB/正式復元、実受験生個人情報・秘密照会キー、常時公式監視・実通知、実モデル推論/高負荷、有料CI/追加課金、技術PRのマージ/公開、本人の署名・承認代理は禁止。単なる運用プロトコルの承認を、これらの実装/運用の許可と読み替えない。

## タスク担当ルール

1. 着手前に Issue を作成し、担当者（`assignee` またはタイトル接頭辞 `[Claude]` / `[Work]`）を明示する。
2. 同一ファイル・同一機能に両エージェントが同時着手しない。着手中は Issue にその旨を記載する。
3. 相手の担当領域（AGENTS.md の表参照）には手を出さない。不明な場合は `research/inbox/` に質問を置く。

## 成果物受け渡しルール

1. 成果物は必ず Pull Request として提出する。
2. PRの説明に「何をテストしたか」「何を検証していないか」を明記する。
3. 他エージェントの成果物を取り込む場合は `research/inbox/` 経由で受け取り、
   取り込み前に独立した検証（テスト実行・差分確認）を行う。

## 競合編集防止

- ブランチ命名規則: `claude/<topic>`、`work/<topic>`。
- 現行の既定ブランチ `master`（将来の `main` を含む）への直接コミットは禁止。レビュー必須の保護ブランチとする（GitHub側設定はPhase Aで整備）。
- 同時編集が疑われる場合は Issue にコメントしてから作業を再開する。

## 事業設計の共有原本（新規提案）

`strategy/README.md` は事業理念・顧客・商品・収益・意思決定のための共有入口（PR #143で採用提案中）。AIや端末からの変更は提案PRに留め、**事業戦略の正式採用・更新の統合はユーザー本人の明示承認を必要とする**。他の開発PRに関する既存の条件付き自律統合の許可を、戦略判断に流用しない。GitHub側の保護設定は別途確認する。
