# INTEGRATION_PLAN.md — Work成果物の統合計画（設計のみ・Workの作業終了後に実施）

Workは現在、Windows夜間ワーカー・既存DB・モデルルーター統合を進行中のため、
本計画は **設計段階** とし、Workの作業完了が確認されるまで実統合は開始しない。

## 想定インポート形式

- Work側から渡される成果物は `research/inbox/` に配置される想定（JSON / SQLite diff / Pythonモジュール等）。
- 形式が未確定の場合、まず `research/inbox/README.md`（Work側に作成を依頼）でスキーマを確認する。

## DB移行方法（案）

1. Work側DBスキーマの差分を独立コピー上で確認。
2. `src/db_qa/` の整合性検査を移行前・移行後の両方で実行。
3. 移行はマイグレーションスクリプト化し、ロールバック手順をセットで用意する。

## 依存関係

- Python版・主要ライブラリのバージョンをWork側と揃える（`requirements.txt` で明示）。
- Work側のDBスキーマに破壊的変更がある場合はIssueで事前合意を取る。

## テスト方法

- 移行前後でレコード数・外部キー整合性・サンプル記事の根拠IDが一致することを確認。
- `tests/` に移行テストを追加し、CIなしでもローカルで再現可能な形にする。

## 差分検査・ロールバック

- 移行前のDBは必ずバックアップし、`reports/` にチェックサムを記録。
- 差分は人間が読めるレポート（追加/削除/変更レコード数、スキーマ差分）として出力。
- ロールバックはバックアップからの復元手順を `docs/` に明記する。

## GitHubへの反映

- 統合作業はすべてPR経由。既存ブランチへの直接コミットは行わない。
- 機密情報（DB内の個人情報等）が含まれる場合は匿名化・サンプリングしたテストデータのみを使う。
