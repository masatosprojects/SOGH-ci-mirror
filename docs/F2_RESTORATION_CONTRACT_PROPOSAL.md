## 3. 復元の記録（案。新しい表は合意が要る）
- **既存の仕組みで足りる範囲**：復元する行は、既存の追記専用の表への追加で表せる。足りないのは**復元の来歴の記録**（どの旧コピー〔SHA〕のどの行を、誰が、いつ、何の判断で戻したか）。
- **案 1（推奨）**：追加の追記専用の表（移行 `0010` の候補）に、復元の事実を 1 件ずつ記録（旧コピーの SHA・表・行ハッシュ・出現番号・復元先の ID・理由・実行者・時刻）。**能力のガード（0004 と同じ）と所有プレフィックスに入れ**、DB-17 の対象にする。**これは凍結済みの移行の変更ではなく、新しい移行の追加であり、合意前に SQL を発行しない。**
- **案 2**：記録は Git の文書と報告（行ハッシュのマニフェスト）だけにする。DB の中の検査が弱い。
- どちらでも：復元イベントは `update_events` の `approved` と**区別**する（head を動かさない）。

## 4. アーカイブ（PR #96 の修正後）に対する受け入れ試験の条件（B-1）
Claude の独立試験（Work のコードは変更しない）。修正後の head ごとに実行：
1. **認証されていない INSERT**：能力を登録しない素の接続で、新しい ID の行（偽の `source_copy_sha256`、偽の `row_sha256`）が**拒否**される。許可された接続でも、**固定マニフェストにない行は拒否**される（完全な内容の allowlist）。
2. 回収行の**欠落・追加・重複**（出現番号）：マニフェストと一致しなければ検証が失敗する。
3. **行順の改変**・**NULL／BLOB／整数／小数／文字列の型の変化**：型付きの往復で検出。
4. **元の表の DDL との不一致**：行に保存した DDL と列順の一致を検査。
5. **トリガー・表の削除／変更**：DB-17（所有プレフィックスの対象）で検出される。凍結 0002〜0009 は変更しない。
6. **再実行**：同じ入力で 0 行追加・バイト同一。**途中失敗**：DDL を含めて全体を巻き戻す。
7. **検証コードとマニフェストの同時改ざん**：同じアカウントが両方を書き換えれば防げない（D2/G-08、`docs/THREAT_MODEL_D2_G08.md`）。検出できるのは外部のベースライン（旧コピーの SHA・Git の記録）との比較で、**正しい外部ベースラインとの比較が残る検査になっているか**を確認する。
8. **出力先**：監査コピーのディレクトリの内側・原本の SHA を持つファイルのあるディレクトリを拒否（G-3）。
9. 既存の Claude 監査の DB-09：baseline=v06 は pass、baseline=v03 は **fail のまま**（アーカイブを履歴復元に数えない）。
