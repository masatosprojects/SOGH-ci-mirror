# 編集・承認・公開の方針（P0-WP0.3 / P7）

**決定（ユーザー、2026-11-01）**
1. **初期運用における編集確認の最終責任者は、ユーザー本人**。
2. **note への非公開下書き保存を、最終公開承認より前に行う。**
3. **記事公開の最終決裁権限は、引き続きユーザー本人に限定する。**
4. **非公開下書き保存には別途明示許可が必要**。この方針は**実際の note 操作を許可しない**。

この文書は将来のフローの**仕様**で、note への実アクセス・下書き保存・公開・本番DBの変更は許可していない。
**AIは記事を生成し、QAを実行できる。しかし、人間の編集確認と公開決裁を自律的に代行できない。**

## 1. 正式な流れ
1. 記事生成（Work の自動処理）
2. 独立QA合格（Claude QA）
3. **ユーザー本人による編集確認**
4. **ユーザーの下書き保存許可**
5. note への**非公開**下書き保存（明示許可後の Work 投稿処理）
6. note 上の表示・本文・リンクの確認（**ユーザー本人**）
7. **ユーザー本人による最終公開承認**
8. 公開（明示承認後の、認可された投稿処理）
9. 必要に応じて訂正・公開停止（ユーザーの決裁に基づく処理）

| 操作 | 許可される主体 |
|---|---|
| 草案生成 | Work の自動処理 |
| 独立QA | Claude QA |
| 編集確認 | 初期運用ではユーザー本人（編集者の追加は将来の明示的な委任のみ。**別のAIや外部担当者に最終権限を与えない**） |
| 下書き保存許可 | ユーザー本人 |
| 非公開下書き保存 | 明示許可後の Work 投稿処理 |
| note 表示確認 | ユーザー本人 |
| 最終公開承認 | ユーザー本人 |
| 公開実行 | 明示承認後の認可された投稿処理 |
| 訂正・公開停止 | ユーザーの決裁に基づく処理 |

そのほかの操作の方針（収集・候補登録・草案生成・ローカル保存・独立QA・承認候補の作成は可能。**自動公開は当面禁止**。有料APIは個別の明示承認。本番ワーカー・スケジューラ操作は別途明示許可）は変わらない。

## 2. 状態（9つ。元の7つの名前は維持）
| 状態 | 意味 | 誰がその状態にするか |
|---|---|---|
| `generated` | 生成済み。QAも確認もまだ | システム（Work の生成） |
| `qa_passed` | 独立QAに合格（**公開承認ではない**） | 独立QA |
| `editor_confirmed` | 編集確認済み | **ユーザー本人** |
| `draft_save_authorized` | note への非公開下書き保存を許可 | **ユーザー本人** |
| `note_draft_saved` | note に非公開の下書きを保存した | 認可された投稿処理（許可の検証後のみ） |
| `note_draft_verified` | 保存した下書きの表示・本文・リンクを確認した | **ユーザー本人** |
| `publish_approved` | 最終公開承認済み | **ユーザー本人** |
| `published` | 公開済み | 認可された投稿処理（最終承認の検証後のみ） |
| `corrected_or_retired` | 訂正・公開停止済み | ユーザーの決裁（実行は投稿処理） |
**QA合格は公開承認ではありません。** `publish_allowed` が false の記事を、CI の成功だけで公開可能にしてはならない。
後方互換：元の7つの状態名（`generated` `qa_passed` `editor_confirmed` `publish_approved` `note_draft_saved` `published` `corrected_or_retired`）は変えていない。追加は `draft_save_authorized` と `note_draft_verified`。**順序は意図的に変わった**：以前の `editor_confirmed → publish_approved` と `publish_approved → note_draft_saved` は無くなり、承認は確認済みの下書きの後になる。

## 3. 状態と「許可・承認のイベント」を区別する
状態は「いまどこか」、イベントは「誰が・いつ・どの版に・何を決めたか」。`draft_save_authorized` と `publish_approved` は進捗ではなく、検証できる決定である。
イベントの契約（`src/db_contract/approvals.py`）：`article_id`、`revision_hash`、`actor`、`action`、`approved_at`（UTC オフセット付きの時刻）、`content_hash`、`target_environment`、`prior_state`、`new_state`（任意：`note_draft_id`、`observed_content_hash`、`reason`、QA結果）。
- **欠けた項目は補完しない**（時刻・actor・ハッシュが無ければ拒否。オフセットの無い時刻、未来の時刻も拒否）。
- イベントは**1つの記事・1つの版・1つの本文ハッシュ**に結ばれる。別の記事・別の版・変更後の本文には使えない。承認後に本文・タイトル・引用する根拠の版が変われば、それは**新しい版**で、`generated` からやり直す（承認は引き継がれない）。
- **AIはユーザーの承認を作れない**：ユーザーの4つの決定（編集確認・下書き保存許可・下書き確認・最終公開承認）には、ユーザーだけが作れる**証明**（イベントのHMAC。鍵はAI・QA・投稿処理が持たず、このリポジトリにも無い）が要る。`actor="user"` と書いただけのイベントは拒否される。**限界**：安全性は鍵の管理に依存する（鍵の保管・配布の方法は未決）。
- **冪等**：下書き保存と公開は、版・本文・操作・対象から作る冪等キーで一度きり。開始して報告の無い試行（クラッシュ）は、盲目的な再試行を止める（下書きが作られた可能性がある）。
- QA結果は本文ハッシュと有効期限に結ぶ。**失効したQA結果では編集確認できない。**
- 保存済み下書きとローカル本文が違えば、下書きは確認できない（`observed_content_hash`）。未知の下書きIDは拒否。公開済みの記事を再投稿できない。
実行できる仕様：`src/db_contract/publication.py`（状態の行列）、`src/db_contract/approvals.py`（イベントと台帳。note には一切接続しない。モックと合成データのみ）、試験 `tests/test_publication_policy.py`・`tests/test_approval_contract.py`（20の負例）。

## 4. 現在の実装状況（過大に主張しない）
| 項目 | 状況 |
