## 4. 版管理された QA ルールの案（契約の変更。合意が要る）
固定文・見出し・出典表記を、重複の判定から**明示的に区別**する必要があるなら、次を満たすこと：
1. **登録制**：除外する並び・行の種類を、版つきのファイル（例：`qa_rules/boilerplate-v1.json`）に**1 件ずつ**登録する。包括的な除外（「注意書きは全部」）はしない。
2. **登録の理由・出典**：各項目に、なぜ必須の固定文か（どの方針・契約の項目に基づくか）、誰が承認したか。
3. **変更履歴**：追加・削除・版を `reports/` に記録し、旧ルールと新ルールを**同じ入力**で比較した結果（件数の変化、消えた指摘の中身）を残す。
4. **真の重複を検出する負例**：本文の叙述・事実の文・同一大学の別方式の記事の意味的な重複を、除外の登録が**あっても**検出すること（登録した固定文に偽装した本文は検出される）。
5. **同一大学の別方式の記事の意味的な重複**を検出する指標（共有する根拠 ID、同じ値の割合、構造を除いた本文の類似度）を、新設して併用する。表層の n-gram だけに頼らない。
6. **しきい値は恣意的に下げない**。除外は「何であるか」で決め、件数で決めない。
7. **本番の記事には、ユーザー承認なしに適用しない。** ルールの追加は、QA の独立性（検査される側が除外を書かない）を保つため、Claude の管轄（Work は提案できるが、登録は QA 側のレビューを経る）。

## 5. H-2：実際の更新経路を検証する受け入れ条件（Work への提示）
合成の経路との差：①基の記事の本文に「合成・未公開」の表示を前置してから `revise_article` に渡している（実際の更新では表示が無い）、②根拠は合成バイトから取り出した値、③QA は元の 13 記事の基準が不合格のまま。**g6 の実データ検証の条件**：
1. 入力は**実際の公式の新しい告知**（合成の fixture と別の入力・別の証拠）。取得は Collector の live 実行（`docs/SOURCE_EVIDENCE_LEVELS.md` の 6）で、保存版との差分が報告される。
2. 記事の本文を**書き換えない**。合成かどうかは、メタデータ・ファイル名・別の DB で表し、`revise_article` に渡す基の本文は実際の更新と同じ。
3. 流れ：SourceSnapshot → 影響分析（変更根拠 1、未評価 0、対象外が変化しない）→ 抽出（hash 固定の設定型抽出器）→ stage（凍結 0002〜0009 の適用済みコピー）→ `revise_article` → QA（既存の export ゲート・記事 QA・引用値ゲート）→ **候補のまま**（`finalize` は呼ばない）。
4. 対象外の記事・根拠は、**生成前に凍結した独立 snapshot と、保存した export を読み戻したものの全項目比較**で不変（H-1 の方式）。
5. 全体 QA が不合格なら保存して停止。**合格するまで有効化候補にしない**。合格は、上記 4 の合意済みルールのもとで。
6. 障害・競合・復旧の再結合（g4 の異常系）を、この更新経路でも実施。
7. 承認（ユーザー）・有効化・公開は別。DB の `approved` は有効化であって公開の承認ではない（`docs/THREAT_MODEL_D2_G08.md`）。
