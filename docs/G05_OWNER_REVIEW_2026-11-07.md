## 3. 版指定のない別名（head を追う）と、固定版が必要な例外の境界
- **既定（維持）：**別名は head に解決する。root と値が同じで、位置だけが違う旧レコード（`same_value_moved`）でも、**登録の経路だけでは固定しない**。別名の `kind`（`locator_corrected_copy` など）、root、case、分類の結果から、固定を**推論しない**。
- **例外（01 の型）：**旧レコードの位置が、root ではなく**現行の head（訂正後の版）だけ**が持っているとき（分類：root とは `same_value_moved`、head とは `duplicate`）、その旧 ID は「その版」を指す記録である。**承認済みの登録だけが、その版に固定できる。**
- **承認済みの登録の条件（コードで強制。`approved_head_id` を渡したときだけ）：**
  1. 登録の時点で、有効 head が承認された版のまま（**同じ SQL 文の中で検査する**）。
  2. `pinned_evidence_id` は、承認された版そのもの（ほかの版ではない）。
  3. レコードは、承認された版と**値と位置が完全に一致**（head の記録との分類が `duplicate`）。
  4. root に改訂が無ければ拒否（固定する版が無い）。
- **例外は、別名ごと**に判断する。root・case・`kind`・サイクルへは波及しない（試験で確認）。02 以降の別名は、通常の登録で、固定しない。

## 4. 同時更新（TOCTOU）の評価と対策
- **評価：**検査（root と head の読み取り、分類）から `INSERT` までが、1 つの原子的な単位ではなかった。別の接続が head を確定すると、旧い承認で別名が登録できた（実測）。
- **対策（実装済み・試験済み）：**承認済みの登録は、`INSERT … SELECT … WHERE (head がちょうど 1 つ) AND (その head が承認された版)` の **1 文**で書く。SQLite は文の開始時に書き込みロックを取るので、呼び出し側のトランザクションの状態によらず原子的で、行数が 0 なら「head が検査と書き込みの間に動いた」として拒否し、**何も書かない**。通常の登録は、head を追うことが契約なので、この問題は起きない。
- **設計の選択の理由：**「関数が自分でトランザクションを開く」方式は、実コピー監査の補助（`real_copy_additive_audit.py`）が 6 組を同じ接続でコミットなしに連続登録するため、不適切（呼び出し側のトランザクションに依存する）。
