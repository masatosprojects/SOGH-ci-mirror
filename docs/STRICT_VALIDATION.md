# 記事の厳密検証（Issue #7）

実装: [src/verify/strict_claims.py](../src/verify/strict_claims.py)（`evaluate_article()` から自動で呼ばれる）
テスト: [tests/test_strict_claims.py](../tests/test_strict_claims.py)

## 何が問題だったか

従来の記事QAは「数値の近くに、実在する引用IDがあるか」しか見ていなかった。
正しい引用IDを付けたまま `30名` を `999名` に書き換えても `ok=True` になった（Issue #7 の再現）。

## 今の検証：本文が、引用した根拠の「値」と一致するか

引用された根拠レコードの構造化値（`value` / `scope` / `fiscal_year` / `proofs`）から
「本文に書いてよい値」を導き、本文の各文と照合する。**根拠に無い値は推測で補わず、検出する。**

| 対象 | 検出カテゴリ |
|---|---|
| 人数・分・字・枚・MB・点・円・倍率（**単位ごと**に照合。漢数字・「1万7000円」・「0.5時間」も正規化） | `quantity_mismatch` / `quantity_not_in_evidence` |
| 日付（西暦・令和・ISO）・時刻・曜日 | `date_mismatch` / `time_mismatch` / `weekday_mismatch` |
| 「A〜B」と書かれた期間は、根拠の（開始, 終了）と**一致し、かつこの順**であること | `period_mismatch` / `period_order_mismatch` |
| 候補日の一覧（`dates`）の一部だけが書かれている | `date_omitted` |
| 入学年度（「2027年度入学」）と試験実施年度（「2026年度に実施」）は**別物**として照合 | `entry_year_mismatch` / `exam_year_mismatch` / `year_mismatch` |
| 入学月（「4月入学」「2027年4月」） | `entry_month_mismatch` |
| 年度内合計を単独枠として書く（`…_aggregate` スコープに「合計」が無い／「単独」と書く） | `scope_reinterpretation` |
| 面接の「実施時間の枠」を実質の質疑時間として書く | `scope_reinterpretation` |
| 「いずれか」の候補日を両日として書く | `scope_reinterpretation` |
| 資格条件の OR（`any_of_*`）と AND（`all_of_*`）の取り違え、項番範囲「（1）〜（N）」 | `logic_mismatch` / `item_range_mismatch` |
| 「第1次／第2次」の取り違え（段階が分かる根拠のみ） | `stage_mismatch` |
| 用紙サイズ（A4→A5）、募集要項のページ参照 `p.N` | `paper_size_mismatch` / `page_reference_mismatch` |
| 根拠のない金額・日付が、引用なしで本文に混入 | `uncited_quantity` |
| 引用の話題と本文が無関係（別の実在IDへの差し替え） | `citation_topic_mismatch` |
| 数値の近くに無い、実在しない引用ID | `unknown_citation` |
| 出典リストのPDFページ・URLが根拠と食い違う | `source_page_mismatch` / `source_url_mismatch` |

「30分の面接時間枠」と「実際の質疑30分」、「年度内AO合計150名」と「夏秋AO単独150名」は、
値が同じでも `scope` / `type` によって区別される（上の `scope_reinterpretation`）。

## 根拠データ側の契約

検証は根拠レコードに次の項目があるほど厳密になる（無い項目は検査せず、推測もしない）。

- `fact_key`、`value`（`count` / `minutes` / `max_characters` / `start`・`end` / `dates` / `date`・`time` / `months` …）
- `scope`（例 `faculty_annual_AO_aggregate`）、`value.type`、`value.selection`、`value.logic`
- `fiscal_year`（入学年度）、`value.period`（例 `all_AO_held_in_2026`）
- `proofs[].page`、`source_url`
- 旧形式（`quota` だけを持つ根拠）でも、人数の照合は行う。

`fact_key` ごとの単位・話題キーワード・選考段階・適用するルールは、コードではなく**登録簿**（`src/verify/data/fact_keys.json`）が持つ。
新しい `fact_key` はデータを足すだけで検証が効く。**未登録の `fact_key` は `unregistered_fact_key`（エラー）として報告し、検証済みにしない。**
手順・重大度・バージョン規則は [FACT_KEYS.md](FACT_KEYS.md)、一覧は [FACT_KEYS_REFERENCE.md](FACT_KEYS_REFERENCE.md)。

## 引用IDの意味的な取り違え（Issue #10）

引用IDが**別の実在する根拠**に差し替わると、本文に数値が無い文では値の照合では見えない。そこで、**引用された根拠の `fact_key` が、その文（段落）の話題と合っているか**を見る。

- **手がかり（`cues`）**：`fact_key` ごとに、その根拠について書く文に現れる言い回しを、登録簿に持つ（文字列、または `re:<正規表現>`）。
  引用する段落に、その手がかりが**1つも無ければ** `citation_topic_mismatch`。手がかりは**識別力**を重視する（例：`first_stage_result` は「第1次…（結果|合格|発表）」、
  `final_result` は「最終…発表」、`interview_scope` は「面接の配点」「面接には」。単なる「面接」や「発表」では、別の根拠への差し替えを通してしまう）。
- **1つの主張＝1つの根拠**：1つの文が複数の根拠を引用するときは、**すべての**根拠の手がかりが段落に必要（片方に合わなければ、その根拠が指摘される）。
- `active` な `fact_key` は手がかりが必須（登録簿の検証）。手がかりの無い `proposed` のキーは、従来の `topic_keywords` で段落に1つ。未登録のキーは制約しない（未登録として報告される）。

測定（Work の実データ。`python -m src.article_qa.mutation_sweep` ＋ `swap_sweep`）：

| | 修正前 | 修正後 |
|---|---|---|
| 引用IDの末尾を書き換え（実在の別IDになる場合を含む） | 筑波・慶應 162/164、新潟 90/95・83/85 | **164/164・95/95・85/85** |
| **各引用を、同じ受け渡しの他のすべての根拠IDに差し替え**（総当たり） | （未測定） | **1,333件中 1,325件（99.4%）**。新潟は 76/76・68/68 |

総当たりで残る8件は、文面が**実際に両方の話題を含んでいる**もの（例：第1次選考の方式の文が「自己推薦書」「志願理由書」を挙げるため、それらの根拠への差し替えと区別できない、
AIの方針の文が「任意提出資料」を挙げる）。**言い回しだけでは原理的に区別できない**ので、限界として残す。

## 作業基準日の検証（Issue #11）

実装: [src/verify/as_of.py](../src/verify/as_of.py)　テスト: [tests/test_as_of.py](../tests/test_as_of.py)

草案の「作業基準日：YYYY-MM-DD」は、その草案の事実を**いつ時点で確認したか**を示し、「既に経過しています」「これから実施」といった時間表現の**基準**になる。
**現在日を時計から読まない**：`reference_date` を引数で渡す（`evaluate_article(..., reference_date=…)`、`run_qa_suite --reference-date 2026-11-01|today`）。
省略すると、現在日に依存する検査（未来かどうか）は**行わない**（実行時刻で結果が変わらない）。テストは固定の基準日を使う。

| カテゴリ | 検出する誤り |
|---|---|
| `as_of_in_future` | 作業基準日が `reference_date` より未来 |
| `as_of_before_retrieval` | 作業基準日が、引用した根拠の `retrieved_at` より前（取得前の状態は書けない） |
| `elapsed_claim_mismatch` | 「締切済み」「既に経過」と書くが、引用した根拠の終了日（`end` / `date` / `dates` の最大）は作業基準日より**後** |
| `upcoming_claim_mismatch` | 「これから実施」「受付中」「締切までに」と書くが、根拠の終了日は作業基準日より**前**（終わっている） |
| `as_of_missing` | 作業基準日が無い（`require_as_of` のとき。根拠を引用する記事のみ） |
| `as_of_unparsable` | 「作業基準日」はあるが日付として読めない（`近日`、存在しない日付） |
| `as_of_conflict` | 異なる作業基準日が複数ある |

- **誤検出を避ける**：同じ日付は指摘しない（日付だけでは、その日の締切時刻を過ぎたか分からない）。引用の無い文（「記載する出願期間・面接日は既に経過しています」）は、
  fact_key 登録簿の `temporal_keywords`（「出願期間」「面接日」…）で根拠に結び付けたときだけ検査し、結び付かなければ**推測せず**何もしない。
  「既に経過」の言い回し・「これから」の言い回しは、登録簿の `temporal_cues` がデータとして持つ。
- **公開前のゲートでは `--require-as-of` を付ける**。既存の古い草案（作業基準日なし）を壊さないよう、既定では欠落を指摘しない。
- 実例：Work の草案10本（筑波・慶應・新潟）は、本検査で誤検出0。新潟の草案に筑波の定型文「出願期間・面接日は既に経過しています」を誤って入れると、
  日程が11月でまだ先なので検出される。

## 定性的な誤り（Issue #9）

数字のない意味の誤り：**共通テスト不要↔必要、持参可↔不可、いずれか↔すべて、希望者のみ↔全員、延長する場合がある↔延長しない、
例外・注記の脱落、限定つきの条件の無条件化、列挙の脱落**。実装は `src/verify/qualitative.py`（エンジン）と、
登録簿 1.5.0 のデータ（`assertions`・`qualitative_rules`・`article_rules`・`lexicons`。`docs/FACT_KEYS.md`）。

- 規則は「この値なら、それを引用する段落は**こう言わねばならず**、**反対を言ってはならない**」。言い回しの一覧は同義語集（`lexicons`）にあり、コードではない。
- 禁止の言い回しは、**同じ文が否定している**（「必須ではありません」）なら許す。
- 規則が及ばない真偽値・注記は、**正しいとは扱わず** `semantic_coverage` に「未検証」として数える（`run_qa_suite` の記事ごとの出力、回帰報告）。
- 一次防御は、Work の**テンプレートが値から文を組み立てる**こと（言い換えが入らない）。Claude の検証は独立した二次防御。

## 根拠にない義務・禁止・免除（Issue #47、登録簿 1.7.0）

**原因**：従来の `semantic_coverage` は、同じ段落に必要性の規則が1つでも適用されると、その段落の他の文の走査を省いていた。検証済みの正しい条件の隣に、
根拠にない新しい義務（例：『生成AIを使用した場合は、大学へ電子メールで事前許可申請することが必須です』）を足しても、矛盾とも未検証とも出なかった。

**今の方式（文・節ごと）**。義務・禁止・免除を述べる節（`claim_wording.obligation`、登録簿のデータ）は、次のどれかに必ず分類される：

| 状態 | 意味 | どこに出るか |
|---|---|---|
| 検証済み | その節を対象とする規則（assertion）が照合し、合格 | 何も出ない（`checked`） |
| 矛盾 | 規則が照合し、根拠と矛盾 | `findings`（記事は不合格） |
| 未検証・未支持 | どの規則も対象としない。節の内容語（漢字・カタカナ）が引用した根拠のどこにも無い | `semantic_coverage.unverified`、`kind=unsupported_obligation`、`ungrounded_terms` つき |
| 未検証・規則なし | どの規則も対象としない。内容語は根拠にある（言い換えの可能性） | 同上、`kind=obligation_without_rule` |
| 検査対象外 | 義務・禁止・免除を述べない節（編集助言、『ご確認ください』）、断定を避ける言い回し（『断定できません』）、引用のない文 | 何も出ない |

- 『対象とする』は、規則の正規表現・3文字以上の語句、または規則が参照する同義語集の語で、**かつ**その同義語集の語の場合は引用した事実の話題語（共通テスト、生成AI…）も同じ節にあること。1〜2文字の語（『使』『認め』）は何も対象にしない。
- **未検証は検出に数えない**。矛盾と断定できない（根拠の言い換えで内容語が変わる正しい文もある）ため、失敗にはせず、未検証として必ず報告する。検出率と未検証件数は別々に出る（`flip_sweep` の `detected` / `declared_unverified` / `silent_misses`）。
- 1つの文に複数の条件があるときは、読点と『…ですが』で節に分け、節ごとに分類する（検証済みの節が、隣の未支持の節を隠さない）。
- 特定の文面を禁止語として登録していない。メール申請の文は、規則の語に当たらず根拠にも無い、という一般の判定で出る。

**測定**：既存10草案の誤検出（失敗の指摘）は 0 のまま。未検証は1納品で 10→13（持参不可の節など、以前は隠れていた3件）。Work の全体ビュー（PR #42）では FAQ の5条件の文は規則が照合し（検証済み）、残る義務の未検証は3件。
注意：根拠を引用する**別の段落**に義務の文を置くと、段落ごとの必須語の規則（`must_any`）が反応して矛盾として検出される（雑音の多い検出）。同じ段落に隠した場合が本件の対象。

## 選考段階（Issue #12・契約確定：案A）

記録に任意の `stage`（記録の最上位。`1`、`2`、`"final"`、またはそれらの空でないリスト）を置ける。**意味は「その記録を引用する文が使ってよい『第N次』の序数」**（ユーザー決定：案A）。
`stage` があれば、引用する文の『第N次選考』がその値に無いとき `stage_mismatch`。`"final"` は序数を照合しない。`stage` の無い記録は従来どおり
（`first_stage*` / `second_stage*` のように登録簿でキーに段階が決まっているものだけ照合）＝後方互換。登録簿の検証：`stage` が不正なら `stage_invalid`、
キーの固定の段階と矛盾すれば `stage_conflict`。

- 登録簿が段階を固定しているキー（`first_stage_result` など）に、他の序数も許す `stage`（例 `[1, 2]`）を付けると警告 `stage_overbroad`（広すぎる）。
- **既知の限界**：1つの文が段階1の記録と段階2の記録を両方引用するときは、使ってよい序数をその和集合として検査する。文の中でどの日付がどの段階かの入れ替えは見えない（日付そのものは別に照合される）。
- **Work に付与してほしい記録**（読み取り専用の走査：序数を使う文が引用する、段階がキーで決まらない記録）：`interview`＝`EV-T27-04-49cb4d`（『第1次選考の合格者には、面接・口述試験を…』）→ `stage: [1]`、`fee_refund`＝`EV-U-2895dfe26d3b`（『第1次選考不合格者を対象に…』）→ `stage: [1]`。
  メモリ上で付与を模擬した測定：旧納品の序数の入れ替え 10/12 → **12/12**、全体ビュー 10/14 → **14/14**（`tests/test_stage_contract.py`、Work のデータは編集しない）。

面接の例：『第1次選考の合格者には、面接を…』が使う序数は **1**（面接の前の段階）で、面接そのものは第2次に属する。したがって `interview.stage = [1]`
（本文が第2次にも触れるなら `[1, 2]`）と書く。`interview.stage = 2`（面接が属する段階）と書くと、この正しい文を誤って指摘する。
Work の付与：記録を引用する文が実際に使う序数を、抽出器・テンプレートの側で持つ（文を値から生成する場合は、その生成が使う序数）。

### 未知の言い換えへの一般化（封印した評価セット D、登録簿 1.6.1）

保留 C を調整に使ってしまったので、**以後 C を独立検証と呼ばない**。新しい未使用の評価セット **D**（`src/article_qa/flip_sealed.py`、29種）を作り、

| | 修正前（1.6.0） | 修正後（1.6.1） |
|---|---|---|
| **D（封印・未使用）** | 94 / 266（35.3%） | **232 / 266（87.2%）** |
| 注意書きの反転（D） | 8 / 42 | **42 / 42** |

未知の言い換えにも効く（Dの注意書き 8→42）。②同義語集に、開発用データで見逃した語だけを追加（任意／要求される・要件／見送ら）。誤検出は 0（既存10草案とWorkの全体ビュー）。

『認められています』→『禁じられています／断られています』（4）、『持参はできません』→『持参も受け付けています』（2）、『下線不要です』→『前提となります』（4）。
これらは同義語集の語彙の外にある言い換えで、語句の規則の限界。**D はここで使い切り**、以後 D を見て調整した場合は独立とは呼べない。

### 述語を保つ規則（登録簿 1.7.1）と、封印セット F

D と E は結果（見逃しの例）を読んだので、**以後は開発用データ**。調整の前に新しい封印セット **F**（29種、`src/article_qa/flip_sealed_f.py`）を作成・コミットし、改善の前後で件数だけを測った。

| | 修正前 | 修正後 | 位置づけ |
|---|---|---|---|

改善の中身：反転の言い回しを列挙せず、**主題の文が閉じた述語の集合を保たねばならない**とした（`assertions` の `sentence_if` / `sentence_must`）。

特定の言い換えは登録していない（F の言い換えが規則に入っていないことをテストで確認）。誤検出（失敗の指摘）は 0（既存10草案・Work の全体ビュー）。

**F の見逃し（16件、F はここで使い切り）**：『認められています』→『の範囲外とされています／拒まれています』（4：許可の述語の語に『補助』という弱い語を残していて、言い換え後も『補助的なツール』に当たる）、
『評価入力が必要です』→『確認の対象ではありません／ご自身でお決めください…』（8：評価者の記録に述語を保つ規則が無い）、『下線不要です』→『必ず確認される項目です』（4：構造化されていない FAQ）。
これらは次の改善の候補だが、**F を見て規則を書いた場合は F を独立とは呼べない**（新しい封印セット G を先に作る）。

## 検出できない誤り（既知の限界）

数値・日付・単位・範囲に関わらない、意味の誤りは検出できない。**QA成功は内容の正しさの証明ではない。**

- 言い換えを伴う定性的な主張。「必要↔不要」などの**代表的な言い回し**は上記（#9）で検出するが、規則に無い言い回しは検出できない（保留 C で 56.8%）。
  条件の具体的な中身、方針の説明の差し替えも同様。見ていないものは `semantic_coverage` の「未検証」に出る。
- 単位なしの数字が、引用から離れた位置にある場合。
- 根拠が段階の序数を持たない文での「第1次」↔「第2次」（例: 面接の根拠を引用する文）。
- 文面が**両方の話題を含む**ときの引用IDの入れ替え（上記「引用IDの意味的な取り違え」。総当たりで 0.6%）。
- **作業基準日（「作業基準日：YYYY-MM-DD」）の値そのもの**: 日付が正しいかを証明する根拠は無い。検出できるのは、現在日・取得日・本文の時間表現と**矛盾する**場合
  （下記「作業基準日の検証」）だけ。矛盾しない範囲で日付を書き換えた場合（例：取得日と現在日のあいだの別の日）は検出できない。
- 日付の表記は上記（#13）の範囲。それ以外（相対表記、月だけ等）は検出しない。
- 根拠レコード自体が誤っている場合（それは原本PDFとの照合＝`src/integration/audit_handoff.py` の役割）。
- 最新の訂正・告知の反映、公開可否の判断。
