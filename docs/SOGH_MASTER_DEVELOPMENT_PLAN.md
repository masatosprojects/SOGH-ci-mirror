## 0. 最終ゴール（North Star）

**大学の公式一次情報を継続的に収集・検証し、対象年度・入試方式ごとに版管理された構造化DBへ登録し、読者に有用な根拠付きnote記事を生成し、人による承認を経て安全に下書き・公開・訂正できる、再現可能で監査可能な継続運用サービス。**

「DB完成」は全国の大学を全部登録した状態ではない。異なる資料様式・年度・方式を**設定追加で安全に処理でき、更新・復旧・監査が成立するデータ基盤**の完成を指す。「公開」は実装上の可能性と、ユーザーによる別途の公開許可を分ける。

### 完成判定を5つに区切る
- **M1 データ基盤完成**：実際の3大学5方式を使い、スキーマ・原典・改訂・復旧・監査・安全な取り込みが端から端まで再現できる。
- **M2 編集制作完成**：DBから記事企画→記事生成→独立QA→修正→承認候補までを再現できる。AIは根拠を創作・改変できない。
- **M3 note下書き統合完成**：明示的な許可を得た隔離環境で、非公開下書き保存・再読込・本文/リンク/画像整合・二重保存防止・失敗再開を実証する。
- **M4 限定運用合格**：指定した少数の大学・記事で、実更新・訂正・監視・障害・人手確認を含む運用手順を実証する。公開は別途承認する。
- **M5 拡張運用合格**：新大学・新方式・新年度が設定と証拠により増やせ、運用負荷・コスト・品質の指標を維持できる。

## 2. 実行モデル（カレンダーではなく「ゲート」）

各Work Package（WP）は次の7項目を必ず持つ。

1. **入力**：依存する原典・確定した契約・既存成果物とそのハッシュ/版。
2. **作業**：コード/データ/文書の具体的な変更。
3. **成果物**：ファイル、API、DBマイグレーション、記事、実行レポート等。
4. **責任者**：Work（実装・収集・DB・記事）／Claude（契約・独立QA・CI・監査）／User（公開・リスク受容・編集方針）。
5. **正例と負例**：動くことに加えて、不正値・誤年度・更新失敗・重複・途中停止で安全に止まること。
6. **完了証拠**：CI run URL、ソースSHA、テスト件数、QA報告、差分、復旧結果、未検証一覧。
7. **Exit gate**：何が満たされれば次の工程へ行けるか。未達ならIssue化して保留し、単に「テストが緑」とは書かない。

進捗状態は `not_started / design / implementing / blocked / QA_pending / accepted / operational`。`accepted` と `operational` は別。各WPに `owner / depends_on / acceptance / evidence_link / blockers / latest_commit` を設ける。

## 3. WBS: 全工程（上から順に必ず全部直列という意味ではない）

### P0 — プロダクト・品質・権限の確定（User＋両者）
- **WP0.1 利用対象**：受験生・保護者・学校のどんな疑問に答えるか、記事タイプ（総合/書類/面接/訂正）と、対象外（合否の断定、個人別資格判定）を定義。
- **WP0.2 情報表示規約**：入学年度と試験実施年度、取得日時と公式公表日、確定情報と未確認、助言と大学公表事実、失効情報、訂正の見せ方。
- **WP0.3 公開決裁**：誰が最終公開を許すか、AI/CIの成功だけでは公開できないこと、公開停止・訂正の責任分界。
- **WP0.4 リスク/予算**：API費用上限、秘密情報・著作権・引用範囲、note規約/操作方法、人間の確認範囲。
- **Gate P0**：判断事項を記録し、非許可の操作（公開/課金/本番タスク起動）を既定denyにしている。

### P1 — 現行資産・データの棚卸し（Work主、Claude監査）
- **WP1.1 システム地図**：既存`SOGH/`本体、`SOGH-collab/`、note旧ボット、DB・ジョブ・Secretsの存在と権限を整理。秘密そのものは共有しない。
- **WP1.2 DBインベントリ**：実スキーマ/テーブル/主キー/外部キー/件数/索引/active head/履歴の構造。原本に触れる監査はコピーで実施。
- **WP1.3 3大学5方式の追跡表**：50根拠と13草案がどの入試サイクル、原典、記事、改訂に繋がるかを一覧化。
- **WP1.4 再現性**：依存バージョン、実行コマンド、`as_of`、入力hash、成果物hashを固定。
- **Gate P1**：第三者が保存した入力からread-onlyで記事13本の構成と根拠を再確認でき、未提供原本を未実施と表示できる。

### P2 — 汎用DB契約と安全な移行（Work実装、Claude契約/監査）【M1の中核】
- **WP2.1 識別子**：大学/学部/学科、入試サイクル（入学年度と実施年度）、方式、公式資料、原典スナップショット、根拠（論理IDと版ID）、記事（論理IDと版ID）。再取得と内容差し替えを区別。
- **WP2.2 原典トレース**：URL、資料種別、取得日時、公表日時（不明はnull）、SHA-256、原文ページ/節/位置、引用。引用・原本の取り扱い方針を遵守。
- **WP2.3 事実スキーマ**：`fact_key`、型、単位、条件・例外、対象年度/方式、適用スコープ、`field_proofs`、不明・保留値。契約の非互換変更は新バージョン。
- **WP2.4 stage契約A**：「記事が使ってよい第N次の序数」を表す任意の`stage`。事実が実施される段階と混同しない。Workが根拠へ付与し、Claudeが変異で確かめる。
- **WP2.5 不変履歴**：原文版、根拠版、記事版、承認版、親版、理由、更新差分。過去行の破壊的更新禁止。同IDで実内容差の衝突を拒否。
- **WP2.6 トランザクション**：候補DB→検証→原子的有効化。途中クラッシュ時のhead不変、バックアップ・ロールバック・再開・通常再実行0登録0改訂。
- **WP2.7 将来の負荷**：新大学追加時の設定だけで増やせる範囲、DBの索引・問い合わせの性能、移行の後方互換性と障害復旧。
- **Gate P2**：複数大学・方式・年度の混同0、旧データの全行不変、実コピーで移行/中断/復旧/再実行を再現。schemaとエクスポート契約が文書化。**DBスキーマが存在するだけでは合格にしない。**

### P3 — 公式資料の取り込みと証拠化（Work主、Claude監査）
- **WP3.1 ソース登録**：許可ドメイン・対象大学・URL・入試サイクル・資料種別、取得ポリシー。
- **WP3.2 取得**：PDF、HTML、訂正告知。取得失敗・404/503・タイムアウト・不正なリダイレクト・文字化け・メンテナンスを判別。
- **WP3.3 原典保存/差分**：ハッシュ固定、必要なローカル原本保全、機微情報のGitHub流出防止、source snapshotと変更理由。
- **WP3.4 抽出器**：大学別のPDF表、段組、別紙、HTML節、表の列ずれ、OCR候補等。曖昧一致・スキャン未検証ではfail closed。
- **WP3.5 出典付き正規化**：値と引用位置、条件/例外、同じ条件を別方式へ横流ししない検査。人間レビューが必要な表セルを列挙。
- **Gate P3**：3大学5方式で原本→根拠レコードを再生成でき、誤ページ・誤年度・曖昧数値・欠落情報で有効化しない。新たな様式の1方式を追加する実地試験にも合格。

### P4 — 更新監視と影響分析（Work収集・Claude版比較）
- **WP4.1 監視器**：URL監視の停止/再開/ロック/リトライ/バックオフ。初回取得、同内容、内容変更、失敗を区別。
- **WP4.2 版差分**：公式内容の変更、移動、訂正、掲載終了、発効・期限切れの分類。
- **WP4.3 影響グラフ**：資料→根拠→記事→投稿先まで到達可能。失効や訂正で影響記事候補を列挙。
- **WP4.4 承認付き差分反映**：正例QAだけでなく原本根拠照合、旧版保全、未確認はpending、再実行時の冪等。
- **Gate P4**：模擬更新と保存原典の本当の差分で、影響記事だけを更新し、誤通知・失敗で前回正常版が失われない。

### P5 — 独立QA・品質保証（Claude主、Workデータ供給）【全工程の横断ゲート】
- **WP5.1 構造QA**：スキーマ、fact_key、年度/方式、原本hash、引用ID、値、日付・期間、数量、`stage`。
- **WP5.2 文章QA**：意味反転、条件/例外、未支持の義務、禁止、免除、別段落の言い換え、出典の取り違え。
- **WP5.3 coverage**：検証済み/矛盾/未検証/対象外の分類。段落に1箇所合格があっても別の義務を見逃さない。
- **WP5.4 回帰**：変異テスト、独立hold-outセット、以前の検出能力・誤検出・skipの回帰。**発見できた割合と未検証として気付いた割合を別計測**。
- **WP5.5 監査**：Work自身の報告に依存せず、納品ファイル/manifest/hash/DBコピー/原典を独立再現。原典未提供ならnot_run。
- **Gate P5**：誤検出が許容範囲、重大な未支持義務が黙って通らない、回帰閾値を下げない、未検証が記事公開可と混同されない。自動検証の限界も明示。

### P6 — 記事企画・制作仕様（Work執筆、Claude検証、User編集方針）
- **WP6.1 記事の目的**：方式概要/書類準備/面接準備/変更速報の各読者ニーズと重複範囲を定義。
- **WP6.2 記事構造**：事実/助言/未確認/出典/作業基準日/変更履歴を分離。必要なら比較表・チェックリスト。
- **WP6.3 コンテンツ組立**：検証済み事実から見出し・文章を生成。現行の決定的テンプレートを基準として保持。
- **WP6.4 AIライター追加の判断**：読みやすさ改善だけを担当させ、数値/義務/出典/適用範囲の変更を禁止。未導入の機能として別プロトタイプで評価、無断課金しない。
- **WP6.5 記事ごとの評価**：正確性、読みやすさ、対象読者への有用性、重複/類似度、重要情報の網羅、情報の期限。
- **Gate P6**：同じ入力で同じ記事版が得られる、変更理由が追跡できる、読みやすさ改善で事実の誤変換が増えない。AI版の採用は基準を満たした場合のみ。

### P7 — 承認ワークフローとnote下書き接続（Work/運用、Claude受け入れ試験）
- **WP7.1 版ごとの公開状態**：generated→QA_pending→review_required→approved_for_draft→draft_saved→approved_for_publish→published→corrected/retired。すべて状態遷移に実行者/理由/時刻を残す。
- **WP7.2 公開ゲート**：公式原本の重要項目照合、現在の年度と期限、未検証項目、人間の最終確認。`CI_green != approved_to_publish`。
- **WP7.3 noteアダプタ**：既存Playwright実装を隔離して検証。まずモック/ローカル、許可後に非公開下書きで実動作確認。noteの最新仕様と利用規約も確認。
- **WP7.4 重複防止と照合**：記事版↔note下書きURL/公開URL、1版1下書き、再試行/切断/保存失敗の処理、本文の再読込照合。
- **WP7.5 配信表現**：タイトル、導入、出典リンク、免責、画像/図の扱い、掲載時点の明示。公開は別権限で明示承認。
- **Gate P7**：明示許可の範囲で非公開下書きの保存→読戻しを再現し、重複・誤版・未承認記事が保存/公開されない。実公開は別途指示まで禁止。

### P8 — 一気通貫E2Eと運用品質（両者＋User）
- **WP8.1 ゴールデン経路**：公式更新→取得→抽出→DB候補→QA→有効化→影響記事改訂→QA→承認→下書きの実演。
- **WP8.2 障害注入**：公式サイト停止、途中クラッシュ、DB書込失敗、CI失敗、ブラウザ保存失敗、認証切れ、同時実行、重複トリガー。
- **WP8.3 復旧**：前回有効版の保護、再開位置、冪等性、手順書、バックアップから復旧。
- **WP8.4 監視・通知**：失敗の通知、長期未更新、期限切れ、原典消滅、差分検出、費用とレート上限。
- **WP8.5 運用権限**：本番タスク/トークン/secretの扱い、承認者不在で停止、監査ログ・手動停止。
- **Gate P8**：成功経路と重大な失敗経路を隔離環境で再現、原典更新や実DBの未確認が残る場合はその範囲を明示。運用自動化開始はユーザーの明示許可後。

### P9 — 限定運用・品質評価（User承認が必要）
- **WP9.1 対象選定**：少数方式、一定の情報量と異なる資料様式を含む対象を選ぶ。
- **WP9.2 公開前レビュー**：大学の最新版、募集要項の注記、数値、期限、未検証、リンク、可読性、誤認を人が確認。
- **WP9.3 試行**：安全な下書き運用を観察。公開は別途承認後のみ実施。
- **WP9.4 実更新**：訂正情報によるDB・記事更新と読者への訂正表示まで追跡。
- **WP9.5 成果指標**：根拠網羅率/原典照合率/重大誤記/差分反映遅延/記事閲覧/保守負荷/人手工数。
- **Gate P9**：誤情報の訂正能力と人間のレビュー手順が機能し、無承認公開・重複投稿が0。停止方法が実効的。

### P10 — 全国展開・継続改善（Work収集主、ClaudeQA）
- **WP10.1 新大学導入パック**：大学情報、対象方式、資料URL/版、抽出プロファイル、fact_key契約、初回原典レビュー、サンプル記事、QA。
- **WP10.2 新年度更新**：旧年度と新年度を明確に分け、昨年度記事を現役記事として使わない。
- **WP10.3 カバレッジ拡大**：方式と地域を増やすごとに異なるPDFレイアウトや例外規則を吸収。
- **WP10.4 運用コスト**：利用API/ブラウザ実行/原典取得/人手監査の負荷と上限を実測。
- **WP10.5 企画改善**：読者が実際に必要とする記事タイプ・更新頻度・検索性を検証し、重複記事を抑制。
- **Gate P10**：新大学を追加しても既存のQAと履歴が壊れず、品質・費用・人手負荷の定義済み範囲を維持できる。

## 4. 依存関係（クリティカルパス）

```text
P0 公開ルール/品質契約
  └→ P1 実資産・DB棚卸し
       └→ P2 汎用DB・原典/根拠/版/記事の正規化
            ├→ P3 公式情報→構造化根拠
            │    └→ P4 差分・影響分析・改訂
            └→ P5 Claude独立QA・受入れゲート（P3/P4/P6/P7/P8を横断）
                 └→ P6 記事企画・生成（最初はテンプレ）
                      └→ P7 人間承認→非公開note下書き
                           └→ P8 end-to-end・故障復旧
                                └→ P9 限定運用（別途許可）
                                     └→ P10 全国展開
```

**並行してよい仕事**：Claudeの品質保証・DB契約とテスト、Workの原典収集・DB移行、記事テンプレート設計、noteアダプタのモック試験。ただし、後段の`accepted`は前段の必要なゲートが合格した後。

| 項目 | 例 |

**状況報告テンプレート**：`達成したゲート / 実行証拠 / 未達・not_run / 新しく発見した欠陥 / 次の依存作業 / 担当 / CI / master SHA`。PRの数やテスト数だけで完成度を判定しない。

## 8. 禁止事項と非完了判定

- CI成功は記事の内容完全保証でも公開承認でもない。
- 未検証を検出成功に加算しない。未知の義務が「未検証」になっただけなら「検出済みの虚偽」ではない。
- 原典の生バイト照合と「公式サイトに引用文字列が見える」は別。
- 旧AI記事ボットのコードが存在しても、入試DBとのnote連携が動作したとはみなさない。
- 公開・課金・秘密情報送信・本番ワーカー/スケジューラの操作は、従来の禁止を維持し、明示承認後のみに限定。
- 全国データの収録が終わるまでDB基盤の完成とみなさない、という無限ゴールは避ける。汎用性は独立した新大学・新年度・別形式の実地試験で証明する。
